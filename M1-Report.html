Executive summary

This project specifies a teaching simulator for deterministic, complete Mealy and Moore machines. It addresses state splitting when different outputs enter the same Mealy state, and explains the extra Moore output before the first input. The local prototype demonstrates both conversions with the assignment examples and custom machine definitions.

The prototype includes machine validation, tables, state diagrams, a reachable-state mapping and aligned execution traces. An editable transition grid and dense-graph navigation remain candidates for M2.

Problem analysis

Students converting output-producing finite-state machines must track both where a transition goes and when its output is emitted. A direct relabeling fails when two transitions enter the same state with different outputs. The simulator makes the construction inspectable and lets students verify the result one input symbol at a time.

Formal model and scope

Both machine types use M = (Q, Σ, Δ, δ, λ, q0), with nonempty finite state set Q, input alphabet Σ and output alphabet Δ, a single q0 ∈ Q, and a total function δ: Q × Σ → Q. Mealy uses λ: Q × Σ → Δ and labels edges a / z. Moore uses λ: Q → Δ and labels states q / z. Every state/input pair has exactly one destination. Partial and nondeterministic machines are outside scope.

For input length n, retain n Mealy tokens and n + 1 Moore trace entries. The Moore trace begins with the initial-state output. Compare tokens after removing exactly the first Moore entry. For a generated Moore machine the fresh start uses a display-only ε, stored internally as None outside Δ, with no incoming edges. An empty input leaves the Mealy sequence empty and the Moore sequence with its initial entry only.

Feasibility study

Technical. Python dictionaries represent total transition functions and enable keyed lookup. Conversion and simulation run locally. Streamlit provides forms and tables. Its Graphviz view renders DOT, with DOT text and tables available as a fallback. State splitting can increase graph size, so tables remain the primary inspection surface for dense machines.

Operational. An instructor can open a supplied exercise, inspect the transition table, convert it and explain the output alignment using input 01. A student can edit transition rows and correct validation errors in place. The prototype uses CSV-style text fields for custom machines. An editable grid and better handling of dense graphs are candidates for M2.

Economic. The local prototype requires Python, the listed packages and a browser. The design assumes access to a student computer and requires no paid hosting, database or external API. Setup, testing and preparation time are the main expected costs. No cost or usability measurements were collected.

Simulator workflow

A failed definition stays in the entry form with an error message. The prototype combines validation, original preview and conversion in one submission. The testing area allows repeated runs and handles invalid input symbols independently of machine validation.

UI wireframes

The three views follow the student's task order. The intended entry view uses a table, with one row per transition and a separate Moore output list. Conversion algorithms

Mealy → Moore

Create one state per reachable destination/output pair. The prototype discovers pairs in breadth-first order using Σ declaration order. The fresh state S models the original start before any input. The pair’s second component records the latest Mealy output. It cannot affect outgoing transitions.

MEALY_TO_MOORE(M):
    create fresh S with display output ε
    queue ← [S]
    while queue is nonempty:
        x ← pop front
        p ← q0 if x = S, otherwise first component of x
        for a in Σ:
            y ← (δ(p, a), λ(p, a))
            if y is new:
                create y with state output equal to its second component
                append y to queue
            add x --a--> y
    return generated Moore machine with initial state S

Labels prefer p_z, with numeric suffixes to avoid display-name collisions. Metadata retains p and z independently. The initial label prefers S with a suffix if S is already an original state. Two distinct reachable outputs entering p yield two copies. Unreachable pairs are omitted.

Correctness. After the first input a, the new state has the original destination and emitted output. Inductively, after k inputs its first component equals the current original state, and its second equals the kth emitted output. Taking another transition preserves both claims. Dropping the pre-input ε gives equality on every word, including the empty word.

Cost. With k = |Σ|, the breadth-first construction visits |Q′| states and creates |Q′|k transitions, with |Q′| ≤ 1 + |Q||Δ|. With keyed dictionary lookup, construction takes O(|Q′|k + |Q|) time and space including the original-state set used for naming. Validation separately scans the original table in O(|Q|k) time, plus alphabet declarations. Exact size depends on distinct reachable incoming outputs. Bounds count symbols as units and assume expected constant-time hashing.

Moore → Mealy

MOORE_TO_MEALY(M):
    preserve Q, Σ, Δ, δ and q0
    for q in Q:
        for a in Σ:
            p ← δ(q, a)
            assign Mealy output λ(p) to transition (q, a)
    return resulting Mealy machine

Correctness. Both runs visit the same states because δ and q0 are unchanged. When input a takes the machine to p, the Mealy edge emits the same λ(p) as the Moore destination. The comparison drops the initial Moore entry, which precedes the first transition.

Cost. Conversion takes O(|Q||Σ|) time and space for the copied table and edge outputs. Simulation uses O(n + |Σ|) time and space for n input tokens, including construction of a symbol lookup set.
